 # Architecture-to-Project Coding Agent

`agent.js` is a terminal-based coding agent that turns Markdown architecture documents into a working project. On each run you can either make the project with an LLM or launch the project already in `Project/`.

The architecture files included in this repository with the `example.` prefix are dummy/sample inputs for demonstrating the agent. They are not hardcoded application requirements and are not the project generated by the agent.

## What the Agent Does

The workflow is:

1. Asks whether to make the project or launch the project already on disk.
2. In Make mode, discovers Markdown architecture files beside `agent.js`, regardless of their filenames.
3. Parses sections, fenced code blocks, PlantUML, and Mermaid diagrams into a structured specification.
4. Derives a build plan from the specification, including components, deliverables, use cases, and the required user-facing surface.
5. Sends the specification and build plan to the selected LLM.
6. Lets the LLM write files, inspect files, list directories, and run project commands.
7. Verifies completion against the filesystem, installs dependencies, and smoke-tests the generated project when its stack is supported.
8. In Launch mode, detects the generated stack, checks prerequisites, and starts the project without an LLM or API key.

The agent is intentionally specification-driven: the architecture documents determine the generated project's components, technology choices, APIs, persistence requirements, security requirements, and deliverables.

## Technology Stack

### Agent

- Node.js 18 or newer, using the built-in `fetch` API
- JavaScript with CommonJS modules
- Node.js built-in modules only: `fs`, `path`, `child_process`, and `readline`
- No `package.json`, npm dependencies, SDK, or build step is required for the agent itself

### LLM providers

The agent supports the following APIs through direct HTTPS requests:

- Anthropic Messages API, for Claude models
- OpenAI Chat Completions API, for GPT models
- Google Gemini `generateContent` API, for Gemini models
- DeepSeek Chat Completions API

The provider, model, API-key tier, and number of keys are selected at startup in Make mode. API keys are held in memory for the current run and are not written to disk by `agent.js`.

### Generated project

The generated project's stack is chosen from the architecture specification. For example, the sample documentation recommends Node.js, Express, PostgreSQL, Redis, RabbitMQ, Elasticsearch, OAuth2, Prometheus, Jenkins, Docker, and Terraform. These technologies are requirements for the sample architecture, not dependencies of the coding agent itself. A different input specification may produce a different stack.

## Project Benefits

- **Turns architecture into implementation:** Converts requirements, diagrams, API contracts, schemas, and technology choices into project files.
- **Broad requirements coverage:** The build plan reminds the model about every detected component and deliverable instead of focusing only on the first feature.
- **Diagram-aware generation:** PlantUML class, sequence, state, use-case, and deployment information is included in the model context.
- **Provider flexibility:** Users can choose Anthropic, OpenAI, Gemini, or DeepSeek and provide multiple keys for rotation.
- **Filesystem-based progress:** The agent measures completion against files that actually exist on disk.
- **Controlled execution:** Generated shell commands run from `Project/`, have a timeout, and are limited by a total command budget.
- **Resumable work:** Existing files remain in `Project/`, so a later run can continue from the current state when a previous run stops early.

## Repository Layout

```text
.
|-- agent.js
|-- README.md
|-- lib/
|-- example.Architecture_Documentation.md
|-- example.Architecture_View.md
`-- Project/                  generated project (created automatically)
```

`Project/` is the workspace where the LLM writes the generated application. Keep architecture Markdown files beside `agent.js`; files inside `Project/` are treated as generated-project files.

## Prerequisites

- Node.js 18 or newer
- An API key for Anthropic, OpenAI, Google Gemini, or DeepSeek when using Make mode
- At least one Markdown architecture document beside `agent.js` when using Make mode
- Internet access to call the selected LLM API in Make mode
- The runtime and package manager required by the generated project when using Launch mode

Make mode creates `Project/` automatically. Launch mode requires an existing project in that directory.

## How to Run

Open a terminal in the repository root. Use the equivalent directory-change
command for your shell, for example:

```text
cd /path/to/Coding_Agent
```

To try the included example specification, copy both example files to any
Markdown filenames beside `agent.js`. For example, on Unix-like shells:

```sh
cp example.Architecture_Documentation.md Architecture_Documentation.md
cp example.Architecture_View.md Architecture_View.md
```

On Windows, use the equivalent file-copy command or your file manager. The
agent ignores common repository documents such as `README.md` when choosing
architecture inputs and creates `Project/` if it does not exist.

Start the agent from the repository root:

```sh
node agent.js
```

At the first prompt, choose one of these modes:

1. **Make the project** — read the architecture documents, ask for an LLM provider and API keys, then build or resume the project in `Project/`.
2. **Launch the project** — use the existing `Project/` folder without an LLM or API key.

For Make mode, the startup prompts ask for:

1. An LLM provider: Anthropic, OpenAI, Google Gemini, or DeepSeek.
2. Whether the API keys use a free or paid tier.
3. The number of API keys to rotate.
4. Each API key, entered when prompted.
5. An optional model name. Press Enter to use the provider default.

The agent writes generated files under `Project/`. It may install dependencies,
run tests, and perform a smoke test before completing. Commands run through the
host operating system's default shell, so generated commands should use tools
available in that environment.

When the agent finishes, it prints a complete run guide containing the exact
commands for the generated project's prerequisites, environment setup,
database setup, installation, application start, browser URL, tests, and API
endpoints. Follow that guide from the generated project directory:

```sh
cd Project
# Run the commands printed in the agent's completion guide.
```

The generated project's technology stack and commands depend on the supplied
architecture documents. Do not assume that every generated project uses the
same package manager, database, port, or start command.

To launch the generated project later, run the agent again from the repository
root:

```sh
node agent.js
```

Choose **Launch the project**. Launch mode detects supported Node.js, Python,
and Go projects, checks dependencies, environment variables, database/cache/
broker prerequisites, migrations, and port availability, then starts the
project. If the project has an Electron script, it launches the desktop window;
otherwise it starts the web or CLI command detected from the project files.

## Agent Limits and Safety Controls

- Maximum of 100 model turns per run.
- Maximum of 5 `run_bash` commands per run.
- Shell commands run with `Project/` as the working directory, use the host OS default shell, and have a 10-minute timeout.
- File tools are restricted to paths inside `Project/`.
- Completion checks skip common dependency/build directories such as `node_modules`, `dist`, and virtual environments.
- API rate-limit and server errors are retried with backoff up to three times.
- Multiple API keys can rotate every 14 turns to help with provider request limits.

These controls limit the agent's execution, but generated code and shell commands should still be reviewed before being used in production.

## Input Document Guidance

Make mode reads every Markdown-like architecture document (`.md`, `.markdown`,
or `.mdx`) beside `agent.js`, except common repository documents such as
`README.md`. Input filenames are not required to follow a fixed convention.
Use one document or several documents. They should describe the system's
requirements and implementation decisions, such as:

- Functional, non-functional, and security requirements
- Components and responsibilities
- Technology choices and recommended defaults
- API contracts and data models
- Database schemas and deliverable filenames
- Traceability information

PlantUML diagrams enclosed by `@startuml` and `@enduml`, and Mermaid diagrams,
are preserved in the structured model context. The LLM can use their actors,
classes, relationships, calls, states, and deployment information.

## Troubleshooting

### Missing architecture files

Make mode requires at least one Markdown, Markdown-like, or MDX architecture
document beside `agent.js`. Filenames are flexible, but `README.md` and other
common repository documents are ignored when another input document exists.
The included `example.*` files are valid sample inputs.

### Missing Project directory

Make mode creates `Project/` automatically. Launch mode requires `Project/` to
exist and contain the generated project.

### Generated run instructions

After a successful or attempted smoke test, the agent writes `Project/RUN.md`
when possible. It contains the detected stack, install and start commands,
browser URL, test command, prerequisites, and troubleshooting notes. Read that
file before starting the generated project manually.

### The run stops before completion

Check the run report for missing components or deliverables. The generated files remain on disk; correct the input documents if necessary and run `node agent.js` again to continue or complete the project.

### API errors or rate limits

Verify the selected provider, model name, network connection, and API key. The agent retries temporary rate-limit and server errors, but authentication and invalid-request errors must be corrected at the provider or prompt.

## Changing API key rotation

Open `agent.js` and edit the top-level setting:

```js
const TURNS_BEFORE_KEY_SWITCH = 14;
```

The default in the current `agent.js` is `14`. This controls how many API
turns each key receives before the agent moves to the next key. For example,
`14` means turns 1-14 use key 1 and turn 15 starts with key 2. Change this
value in `agent.js` if your provider's rate limit requires a different
rotation. The value affects key rotation only; `MAX_TURNS` still controls the
total run limit in `lib/config.js`.
