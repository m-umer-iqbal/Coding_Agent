 # Architecture-to-Project Coding Agent

`agent.js` is a terminal-based coding agent that turns software architecture documents into a scaffolded project. A user supplies an `Architecture_Documentation.md` file and an `Architecture_View.md` file, chooses an LLM provider, and the agent asks that model to create the implementation inside the `Project/` directory.

The architecture files included in this repository with the `example.` prefix are dummy/sample inputs for demonstrating the agent. They are not hardcoded application requirements and are not the project generated by the agent.

## What the Agent Does

The workflow is:

1. Scans the working directory for `Architecture_Documentation.md`, `Architecture_View.md`, and `Project/`.
2. Parses the documentation into sections and extracts fenced code blocks.
3. Parses PlantUML blocks from the architecture view and stores their names and source.
4. Derives a build plan by identifying components and named deliverable files in the specification.
5. Sends the structured specification and build plan to the selected LLM.
6. Lets the LLM work through tools to write files, inspect files, list directories, and run project commands.
7. Checks the filesystem when the LLM requests completion. Completion is rejected while required components or deliverables are missing.
8. Prints a run report and, when provided by the model, a complete guide for running the generated project.

The agent is intentionally specification-driven: the architecture documents determine the generated project's components, technology choices, APIs, persistence requirements, security requirements, and deliverables.

## Technology Stack

### Agent

- Node.js 18 or newer, using the built-in `fetch` API
- JavaScript with CommonJS modules
- Node.js built-in modules only: `fs`, `path`, `child_process`, and `readline`
- No `package.json`, npm dependencies, SDK, or build step is required for the agent itself

### LLM providers

The agent supports the following APIs through direct HTTPS requests:

- Anthropic Messages API, for Claude models
- OpenAI Chat Completions API, for GPT models
- Google Gemini `generateContent` API, for Gemini models

The provider, model, and API keys are selected at startup. API keys are held in memory for the current run and are not written to disk by `agent.js`.

### Generated project

The generated project's stack is chosen from the architecture specification. For example, the sample documentation recommends Node.js, Express, PostgreSQL, Redis, RabbitMQ, Elasticsearch, OAuth2, Prometheus, Jenkins, Docker, and Terraform. These technologies are requirements for the sample architecture, not dependencies of the coding agent itself. A different input specification may produce a different stack.

## Project Benefits

- **Turns architecture into implementation:** Converts requirements, diagrams, API contracts, schemas, and technology choices into project files.
- **Broad requirements coverage:** The build plan reminds the model about every detected component and deliverable instead of focusing only on the first feature.
- **Diagram-aware generation:** PlantUML class, sequence, state, use-case, and deployment information is included in the model context.
- **Provider flexibility:** Users can choose Anthropic, OpenAI, or Gemini and provide multiple keys for rotation.
- **Filesystem-based progress:** The agent measures completion against files that actually exist on disk.
- **Controlled execution:** Generated shell commands run from `Project/`, have a timeout, and are limited by a total command budget.
- **Resumable work:** Existing files remain in `Project/`, so a later run can continue from the current state when a previous run stops early.

## Repository Layout

```text
.
|-- agent.js
|-- README.md
|-- example.Architecture_Documentation.md

```

`Project/` is the workspace where the LLM writes the generated application. Keep the agent's input documents beside `agent.js`; they are not read from inside `Project/`.

## Prerequisites

- Node.js 18 or newer
- An API key for Anthropic, OpenAI, or Google Gemini
- Architecture input files named exactly:
	- `Architecture_Documentation.md`
	- `Architecture_View.md`
- A `Project/` directory beside `agent.js`
- Internet access to call the selected LLM API

## How to Run

Open a terminal in the repository root:

```powershell
cd C:\Users\HP\Desktop\Coding_Agent
```

If you want to use the supplied dummy documents, copy them to the filenames expected by the agent:

```powershell
Copy-Item example.Architecture_Documentation.md Architecture_Documentation.md
Copy-Item example.Architecture_View.md Architecture_View.md
```

Then start the agent:

```powershell
node agent.js
```

Select 1st option 

The startup prompts ask for:

1. An LLM provider: Anthropic, OpenAI, or Google Gemini.
2. Whether the keys are free or paid tier keys.
3. The number of API keys to use.
4. Each API key, entered one at a time.
5. An optional model name. Press Enter to use the provider default.

The generated files will appear under `Project/`. The exact application start and test commands depend on the architecture specification and are reported by the agent when the model calls `task_complete`.

Then, in the terminal, run the agent again:

```powershell
node agent.js
```

Now select the 2nd option and answer all the questions of the system

## Agent Limits and Safety Controls

- Maximum of 100 model turns per run.
- Maximum of 5 `run_bash` commands per run.
- Shell commands run with `Project/` as the working directory and have a 3-minute timeout.
- File tools are restricted to paths inside `Project/`.
- Completion checks skip common dependency/build directories such as `node_modules`, `dist`, and virtual environments.
- API rate-limit and server errors are retried with backoff up to three times.
- Multiple API keys can rotate every 14 turns to help with provider request limits.

These controls limit the agent's execution, but generated code and shell commands should still be reviewed before being used in production.

## Input Document Guidance

`Architecture_Documentation.md` should describe the system's requirements and implementation decisions, such as:

- Functional, non-functional, and security requirements
- Components and responsibilities
- Technology choices and recommended defaults
- API contracts and data models
- Database schemas and deliverable filenames
- Traceability information

`Architecture_View.md` should contain named PlantUML diagrams enclosed by `@startuml` and `@enduml`. The agent preserves these diagrams in the structured model context so the LLM can use their actors, classes, relationships, calls, states, and deployment information.

## Troubleshooting

### Missing architecture files

The agent requires the exact filenames `Architecture_Documentation.md` and `Architecture_View.md`. Rename or copy files with another name, such as the included `example.*` files, before running it.

### Missing Project directory

Create the output directory beside `agent.js`:

```powershell
New-Item -ItemType Directory -Path Project
```

### The run stops before completion

Check the run report for missing components or deliverables. The generated files remain on disk; correct the input documents if necessary and run `node agent.js` again to continue or complete the project.

### API errors or rate limits

Verify the selected provider, model name, network connection, and API key. The agent retries temporary rate-limit and server errors, but authentication and invalid-request errors must be corrected at the provider or prompt.

## Changing API key rotation

Open `agent.js` and edit the top-level setting:

```js
const TURNS_BEFORE_KEY_SWITCH = 4;
```

This controls how many API turns each key receives before the agent moves to the next key. For example, `4` means turns 1-4 use key 1 and turn 5 starts with key 2. This is a user setting in `agent.js`, so a professor can change it without searching through the `lib` folder. The value affects key rotation only; `MAX_TURNS` still controls the total run limit in `lib/config.js`.
